## 症状

打断一轮对话后，点用户气泡上的铅笔改一下内容再发，气泡下方出现：

```
网络断开，恢复连接后将自动发送
```

而实际上网络从未断开，服务器也早已受理并在正常干活。表现出三种样子：

1. 回答最后照样出来了，但中间显示过一次断线
2. 界面一直停在等待状态，刷新也不恢复
3. 点中断后重新发送，又是同一句「网络断开，恢复连接后将自动发送」，而这条消息永远不会自己发出去

普通发消息从不出现，只有编辑气泡重发、重新生成会中招。

---

## 复现

### 事故会话的共同特征

- `data/workspace/sessions/8508ebf8cb074cf2bd0f1961cd54e7eb/events.jsonl`
- `data/workspace/sessions/369f245bb3b14f5a98f0ff5f80ae7fcc/events.jsonl`

两个会话都有同一个特征：**写下 `user_message` 的 task 和真正干活的 task 不是同一个**，中间隔了 42 秒（8508 会话 id=16 到 id=17）甚至 13 分钟（369f 会话 id=83 到 id=84）。说明每一次都走了重发路径，第一次的受理没被前端认下。

### 稳定复现步骤

用 `_t_probe_browser_edit.py` 驱动真实浏览器：发一条需要调工具的消息，8 秒后点中断，0.5 秒后打开用户气泡的行内编辑并提交。

修复前的帧时间线：

| 时刻 | 事件 |
| --- | --- |
| 12.17s | 前端发出 `edit_and_regenerate`，`messageId=fbeead62-...` |
| 12.20s | 服务器回 `message_accepted`，`data.messageId` 与发出的完全一致 |
| 20.18s | 前端仍当作没收到，原样重发，被服务器以 `task_active` 拒绝 |
| 28.20s | 弹出「网络断开，恢复连接后将自动发送」，此时第一个任务正在正常输出 |

受理帧只用了 30 毫秒就到达浏览器，编号也完全对得上，前端却没认。

### 定位到根因的关键一测

在页面里同时取两个 URL 的模块，查同一个 `messageId` 的待确认记录：

```
{"sameModule": false, "editMessageId": "fbeead62-...",
 "retryCountInAppInstance": 0, "retryCountInHandlerInstance": -1}
```

`sameModule: false` 说明是两个模块实例；这条待确认记录在 `app.js` 用的那份里存在（返回 0），在处理受理帧的那份里查不到（返回 -1）。

## 原因

浏览器按 URL 缓存 ES 模块。`./ws.js?v=23` 和 `./ws.js` 是两个不同的 URL，于是 `ws.js` 被加载成两份，各自持有一份私有的 `pendingAcks`（待确认消息表）、`outbox`（失败重发队列）和心跳定时器。

全站只有 `app.js` 引用时带了版本号，其余全部不带：

- `app.js`：`from "./ws.js?v=23"` → 实例 A
- `message-handler.js`、`input.js`、`conversations.js` 等：`from "./ws.js"` → 实例 B

由此分出两条命运不同的链路：

- 普通发消息走 `input.js` 里直接 import 的 `sendReliable`，登记在 B；受理帧由 `message-handler.js` 的 `resolvePendingAck` 处理，查的也是 B。对得上，一切正常。
- 编辑重发走 `chat-ui.js` 的 `state.api.sendReliable`（这个 `state.api` 是 `app.js` 挂上去的，属于 A），登记在 A；受理帧仍由 B 处理。A 里那条记录永远解不开。

于是 A 的 8 秒定时器照常触发（`ACK_TIMEOUT_MS = 8000`），原样重发一次；重发正好撞上第一次已经跑起来的任务，被服务端以 `task_active` 拒绝；再 8 秒后判定 `ack_timeout`，而 `isNetworkFailure` 把 `ack_timeout` 归为网络故障，于是打出「网络断开」。

`outbox` 同样是分裂的：失败后 `chat-ui.js` 用 `state.api.enqueueOutbox` 把消息排进 A 的队列，而负责发出去的 `flushOutbox` 只被 `message-handler.js`（B）调用。A 的队列永远不会被 flush，所以「恢复连接后将自动发送」是句空话，界面就此永久卡住。

WebSocket 本身存在共享的 `state` 对象里，两份实例都能正常收发，所以只有模块私有状态会分裂，问题才表现得如此隐蔽。

除 `ws.js` 外，`assets.js`、`conversation-sync.js`、`model-controls.js`、`modules/asset-system/asset-store.js` 也被引用成两份，属同一类隐患。

---

## 修复

把模块之间互相引用时的版本号全部去掉，让每个模块在浏览器里只有一个 URL、一份实例。缓存失效交给已有的 `_no_cache` 中间件，不再靠人手维护版本号一致。

保持人工版本号一致做不到：漏写一处就分裂出一份独立状态，而且症状远离原因，极难定位。

`index.html` 里两个 CSS 的 `?v=` 保留未动。CSS 不是模块、没有私有状态，重复加载不会分裂，且同样被 `_no_cache` 覆盖。

## 验收

同一复现流程，修复前后对比：

| 观察项 | 修复前 | 修复后 |
| --- | --- | --- |
| 编辑重发实际发送次数 | 2（8 秒后自动重发） | 1 |
| 受理帧是否被认下 | 否 | 是 |
| 服务端 `task_active` 拒绝 | 有 | 无 |
| 「网络断开」横幅 | 28 秒时出现 | 不出现 |
| 回合结果 | 答案照样出来，但界面显示断线 | 正常流式输出到结束 |

探针断言：`{"pendingAckResolved": true, "editSendCount": 1}`。

手工验收：发一条消息，中途点中断，再点用户气泡的铅笔改内容重发。应当直接进入流式输出，不出现任何断线提示，也不产生第二个 task。

另需确认全站模块引用一致：`apps/nextagent` 下的 `.js` 与 `.html` 中，`import` 与动态 `import()` 的路径不应再带 `?v=`。
