# 回合状态前后端不一致修复记录

日期：2026-11-02

## 症状

一轮对话因为工具出错停止、用户又点了停止、随后再发一条，界面卡在：

- 发送键一直是「停止」（蓝方块），点下去还要再取消一次
- 对话底部一直挂着一行「等待回复中」
- 最后一条工具块是 `Write · 未收到工具结果(回合被中断)`

也就是说：**后端早就认为这一轮结束了，前端仍认为它在跑。** 刷新能恢复，不刷新就一直卡着。

## 根因

「某线程此刻有没有回合在跑」这件事，被拆成了四份互不相认的副本：

| 位置 | 载体 | 靠什么清除 |
|---|---|---|
| 后端 | `_thread_active_tasks` | 回合的 `finally` 里 `unmark_thread_task` |
| 后端 | `EventBus.finished_at` | `event_bus.close` |
| 前端 | `taskMirror` / `taskToConv` | `_cleanupStream` ← 只由 `turn_complete` 触发 |
| 前端 | `cs.currentTaskId` / `liveTaskId` / `retainedTaskId` | 同上 |

四份账**只能靠 `turn_complete` 这一帧对账**，而它是易失的 WS 帧。具体失效点是：

1. `turn_complete` 走 `acceptSeq(msg)` 去重。`turn_resume` 会把 `taskLastSeq[task]` 直接设成总线快照的 `last_seq`，一旦快照取在 `turn_complete` 入总线之后、实时帧到达之前，`turn_complete` 就被判成重复帧丢掉 —— 状态永不收尾。
2. `stream_error` 和 `turn_complete` **两条路径都收尾**，而 `stream_error` 还有一个「`taskId !== cs.currentTaskId` 就丢进 `_pendingReconnect`」的分支，会让收尾静默失效。
3. `retainedTaskId` / `retainedUntil` / `RETAINED_STREAM_WINDOW_MS` 这套 5 秒窗口机制，从未被用于渲染，却通过 `composer.js` 里 `!cs.retainedTaskId` 条件变成了一个隐藏的状态闩。
4. 后端在 `mark/unmark` 时**不推送**名单，前端只有 `auth` / `thread_focus` 两个时机能拿到权威状态 —— 一旦错过，没有任何自愈路径。

对照 `D:\deepseek-harness` 的做法：那边「在跑」是从 Host 的 Agent 对象**读出来**的（`agent.status === 'running'`），状态帧是完整替换且支持周期性重读，回合结束是持久事件 `turn/end`。**状态可反复读取 > 两端维护一致性。**

## 改法：一份权威，三条规则

### 1. 后端：`_thread_active_tasks` 是唯一权威

`ws_chat.py`

- 新增 `publish_tasks()` / `_broadcast_tasks()`：名单一变就 `broadcast` 一份 `tasks_snapshot`。
- `mark_thread_task` / `unmark_thread_task` 各自推一次（`unmark` 的推送排在 `schedule_pump` 之前，避免下一轮先 mark 导致按钮闪）。
- 新增 `sync_state` 帧：前端认为有回合在跑时，可以主动要一份权威名单 + 该会话的队列状态。
- 顺手把散落的 `asyncio.create_task` 收进 `_spawn(coro, label)`（带失败日志），删掉只服务于 `schedule_pump` 的 `_pump_done`。

### 2. 前端：`reconcileTasksSnapshot` 是唯一收敛点

`static/js/message-handler.js`

- `reconcileTasksSnapshot(tasks)`：名单里没有的镜像行 = 那一轮结束了 → 删镜像 + 调 `finishThreadTurn(cs)`。
  - 多一份 `busyConv` 判断：同一会话还有别的在跑回合时，不拔掉等待提示。
- `finishThreadTurn(cs)`：**唯一的收尾入口**（清等待提示、清流式指针、清 pendingSend、重算 composer），幂等。它不碰 `taskMirror`。
- `turn_complete` / `stream_end` 降级为「快去看一眼」：`_onTurnComplete` 只做
  `requestTasksSnapshot()` + 资源刷新，**不自己改状态**。对账语句放在最前面，避免显示副作用抛错把状态收敛挡住。
- `stream_error` / `error` → `_showStreamError`：**只画一条错误气泡**，不动任何状态。
- 自愈：`startSyncProbe()` 在前端仍认为有回合在跑时，每 3 秒发一次 `sync_state`；后端说没有了就收敛，探测随之停下（没有在跑的回合时完全不发）。

收敛关系因此变成：

```
_thread_active_tasks 变更 ──▶ tasks_snapshot ──┐
前端 turn_complete ─────────▶ sync_state ─────▶ reconcileTasksSnapshot ──▶ finishThreadTurn
前端 3s 探测 ───────────────▶ sync_state ─────┘
```

三条触发、一个收敛函数。任何一帧丢失都由下一次推送或探测纠回来。

### 3. 删掉的死代码

`message-handler.js`：

- `RETAINED_STREAM_WINDOW_MS`、`_clearRetainedStream`、`cs.retainedStreamBubble/retainedTaskId/retainedUntil`
- `_cleanupStream`（拆成 `finishThreadTurn` + 镜像删除搬到 reconcile）
- `_applyStreamTaskError`、本地重复的 `_isInflightStatus`、`isActive`
- 整套从未被调用的远端遮罩：`_showRemoteToolOverlay` / `_hideRemoteToolOverlay` / `_doHideOverlay` / `_forceHideOverlay` / `_remoteToolOverlay` / `_beforeUnloadHandler` / `_REMOTE_TOOL_NAMES`、`_showRemoteStopNotice`、`REMOTE_STOP_NOTICE_WINDOW_ID`、`_escapeHtml`，以及随之不再需要的 window-manager 引用
- 后端从不发送的 `stream_end` 监听、与 reconcile 末尾重复的 `tasks_snapshot` 监听
- 12 个用不到的 `chat-ui` / `history` / `asset-catalog` / `format` 导入

`composer.js`：`applyComposerState` 不再清 `currentTaskId`（它记的是「直播 DOM 属于哪一轮」，回合结束后仍要留着给迟到的块事件用），也不再读 `retainedTaskId`。

`state.js`：删掉 `retained*` 三个字段。

净减少约 110 行。

## 需要守住的不变量

1. **只有 `reconcileTasksSnapshot` 能删 `taskMirror` / `taskToConv`**（`_onTurnComplete`、`stream_error` 都不许碰）。
2. **`turn_complete` 不是状态权威**：它只触发对账。丢了不影响正确性，只影响那一次收尾快多少。
3. **`finishThreadTurn` 幂等**，可以因为推送和探测被重复调用。
4. **后端 `mark`/`unmark` 必须推名单**，不许只在 `turn_complete` 里收尾。

## 测试

新增：

- `apps/nextagent/test_task_state_sync.py`（7 个）
  - `mark` / `unmark` 各自推 `tasks_snapshot`，名单内容正确
  - 旧回合迟到的 `unmark` 不抹掉新回合
  - `_active_tasks_payload` 与 `_thread_active_tasks` 完全一致，且带前端要读的字段
  - `sync_state` 入口存在；名单推送确实挂在 `mark`/`unmark` 上（防回归的源码断言）
- `apps/nextagent/js_tests/turn-state.test.mjs`（10 个，真跑前端状态机）
  - **`turn_complete` 丢失时，后端空名单也能把界面收回发送态** ← 本次 bug 的回归测试
  - 后端说在跑就绝不能被误判成结束
  - `stream_error` 只画错误块、不收尾
  - `turn_complete` 只是触发一次对账
  - 显示刷新抛错也挡不住状态收敛
  - 旧回合迟到的 `turn_complete` 不打乱新回合
  - 同会话残留旧镜像行不会拔掉新回合的等待提示
  - 「出错 → 停止 → 再发一次」最后仍回到发送态
  - 探测只在还认为有回合在跑时发 `sync_state`
- `apps/nextagent/test_frontend_turn_state.py`：把上面那组挂进 `unittest discover`，找不到 node 就 skip。

前端能测的原因：`static/js` 只有 `ws.js` 在模块顶层碰了 `window`，其余全是函数内的 DOM 调用。`js_tests/dom-stub.mjs` 提供了够用的最小 DOM（元素树 + `.a.b` / `[attr="v"]` 选择器），所以这些浏览器 ES 模块可以直接在 node 里 import。

跑法（这台机器没有全局 node，用自带的那份）：

```powershell
# 前后端一起
& E:\mafagent\python\python.exe -m unittest discover -s apps/nextagent -p "test_*.py" -t .

# 只跑前端状态机
& "E:\mafagent\python\Lib\site-packages\playwright\driver\node.exe" apps\nextagent\js_tests\turn-state.test.mjs
```

也可以 `set MAFAGENT_NODE=<node 路径>` 指定解释器。

当前基线：`Ran 83 tests`，其中 2 failures + 5 errors 都是本次改动之前就存在的环境问题（缺 ripgrep × 4、`apps.nextagent.retrieval` 导入失败、`test_session_ui_jsonl` 前端持久化门），与本改动无关。

## 未做（留待后续）

- `turn_end` 目前已经写进 `events.jsonl`，但被 `session_log._PROJECTED` 明确排除、不下发前端。真正做到「刷新也能从日志推导回合闭合」需要让它参与投影 —— 当前靠 `auth` 时的 `tasks_snapshot` 已经覆盖刷新场景，所以这次没动投影层。
- `_showRemoteStopNotice`（点停止后提示「远端任务可能还在跑」）随遮罩一起删了：它的触发条件是 `_remoteToolOverlay`，而那个遮罩从来没有被打开过，属于从未生效的死分支。如果确实需要这个提示，应重新设计触发条件（例如「停止时该回合还有未返回的工具调用」），而不是恢复旧代码。
